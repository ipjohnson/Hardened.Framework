1. Summary

The AWS line was rebuilt today around one idea: a host makes three decisions (payload to request, response to payload, who owns the invocation loop) and everything between is the shared pipeline. Handlers name a neutral trigger, [Queue("orders")], and a build property on the runtime package decides which adapter serves it. The second and third clouds are therefore mostly adapters, one host each, and the test fidelity ladder that already exists for AWS.

Two things are not just adapters. Azure needs a source generator, because the isolated worker discovers functions from metadata, and the Functions SDK's own generator cannot see code that Hardened's generator emits. GCP needs no new transport at all: Cloud Run is a container listening on PORT, which Kestrel already is, so the GCP line is a front door that turns Pub/Sub push, Eventarc CloudEvents and Cloud Scheduler requests into trigger routes.

The work runs as two agents in one repository. Each owns a cloud directory under src/Clouds and works in its own git worktree on its own branch; shared members change only through a message to the orchestrator and the peer, applied on main, after which both rebase. The user-facing claim to hold at the end: a handler written for AWS moves to Azure or GCP by changing a package reference, and the same test file passes at every fidelity level, including in a container against the cloud's own emulator.

Azure line

Isolated worker. Core runtime plus one adapter package per trigger family, a generator that writes the function shims and the worker metadata, envelope-level testing, a Functions-host container tier over Azurite, the Service Bus emulator and the Event Hubs emulator.

GCP line

Cloud Run on Kestrel. A trigger front door for Pub/Sub push, Eventarc CloudEvents and Scheduler, PORT and SIGTERM handling, a shared CloudEvents package, and a container tier over the Pub/Sub emulator and fake-gcs-server.

Simulator tier

A fourth rung on the fidelity ladder: the published function in the cloud's own host container, driven by the cloud's own emulator through Testcontainers, observed through the container's output. Required in CI, honest where no emulator exists.

3. Decisions to confirm

Each card states a recommendation and what the plan looks like if the answer is no. Everything after this section assumes the recommendations.

D1 · Repository

HardenedCloud is a clone of Hardened.Framework, and the lines land under src/Clouds

The empty ~/HardenedCloud directory has no git history and no matching GitHub repository. Today's consolidation made the framework, the cloud packages and the site one repository on one version, and AGENTS.md already reserves a solution filter per cloud. The Azure generator also has to compile Hardened.SourceGenerator from source to reach TriggerModuleGenerator.Triggers, which only works inside this repository.

Recommendation: clone ipjohnson/Hardened.Framework into ~/HardenedCloud and build there on branches cloud/azure and cloud/gcp, merged to main by pull request. If no: a separate repository consuming published packages reintroduces the sibling-checkout and version-skew hazards the consolidation removed, and the generator would have to restore Hardened.SourceGenerator as a package. Roughly a week of extra plumbing and a permanent drift risk.
D2 · Azure model

Isolated worker, and Hardened writes the function metadata itself

The in-process model retires on 2026-11-10, so the isolated worker is the only candidate. Its host discovers functions from metadata: the Worker SDK's build task writes functions.metadata and extensions.json by scanning the compiled assembly for [Function], and its Roslyn generator emits an IFunctionMetadataProvider for worker indexing. That generator cannot see Hardened's generated code, because generators never see each other's output. So Hardened's generator emits three things from the neutral triggers: a [Function] shim per handler carrying the real binding attribute, its own IFunctionMetadataProvider, and its own IFunctionExecutor. The SDK's post-build scan still runs over the compiled shims, so extensions.json is produced; the SDK's empty generated provider and executor are kept out with FunctionsAutoRegisterGeneratedMetadataProvider=false and FunctionsAutoRegisterGeneratedFunctionsExecutor=false, set by the runtime package's targets.

Recommendation: as described, proven by spike S1 in Phase 1 before any adapter is written. If no: the only alternative is asking applications to write [Function] methods by hand, which puts the cloud back in the handler file.
D3 · GCP target

Cloud Run services on Kestrel, events as CloudEvents over HTTP; Cloud Functions stays out

Cloud Run is a container on PORT with a SIGTERM and ten seconds to drain. Kestrel already serves that. Eventarc delivers every event as a CloudEvents 1.0 binary-mode POST, Pub/Sub push delivers a documented JSON body, and Cloud Scheduler is an HTTP target. The Functions Framework for .NET is an ASP.NET Core application, so targeting Cloud Run functions would break the no-ASP.NET constraint for nothing; those functions run on Cloud Run underneath anyway.

Recommendation: Cloud Run only, with a trigger front door in the Kestrel host. If no: a Functions Framework adapter is a separate, ASP.NET-shaped line and is not in this plan.
D4 · Trigger gaps

Stream on GCP and direct invoke on Azure stay unbound in this pass

GCP has no sharded, checkpointed stream a [Stream] handler can be moved to; Pub/Sub ordering keys are not that. Azure has no direct invoke; the nearest thing is an HTTP trigger with a function key. Leaving both unbound means HRDF001 names the gap at build time rather than a package pretending.

Recommendation: unbound, with the diagnostic text naming the provider. GCP serves [HardenedFunction] as POST /_triggers/invoke/{operation} because Cloud Run services are invoked over HTTP anyway. If no: add an Azure HTTP-backed invoke adapter in Phase 4, about a day.
D5 · Queue and Topic on Pub/Sub

A queue is a push subscription, a topic is an Eventarc delivery

Both neutral triggers map to Pub/Sub, and the delivered request has to say which. A plain push body carries the subscription name and not the topic; an Eventarc delivery carries the topic in ce-source. So [Queue("orders")] routes on the subscription named orders (competing consumers, one service), and [Topic("order-events")] routes on the topic named in the CloudEvent source (fan-out through Eventarc).

Recommendation: as above, documented on both attributes' GCP pages. If no: a naming convention on subscriptions could stand in for topics, at the cost of a rule the deployment has to know.
D6 · How the agents work

Two worktrees on one clone, shared members changed only through a request

Both agents building one working tree at once would race on obj/ and bin/ and see each other's half-finished edits. A git worktree per agent keeps one repository and one history while giving each a consistent tree; Claude Code's worktree isolation also physically stops an agent editing outside its own tree. Shared members are changed on main by the orchestrator from a structured request the agent sends, and both agents rebase. Section 4 has the protocol.

Recommendation: worktrees plus the request protocol, with agent teams enabled so the two can message each other directly rather than through the orchestrator. If no: the same protocol works with the orchestrator relaying every message; only latency changes.
D7 · Simulator tier in CI

Container tests are required in CI, and the matrix says where fidelity stops

Docker is on the GitHub runner, Testcontainers has modules for every emulator this plan uses, and the repository's own rule is that Docker tests fail rather than skip. Where a cloud has no emulator, the top rung is the container running the cloud's host with a hand-built request, and the matrix in section 7 says so per trigger rather than claiming a tier that does not exist.

Recommendation: a separate simulators CI job, trait-filtered, running after the build in parallel with the AOT probes. If no: the container projects still exist and run locally; CI time stays where it is.
D8 · Shared CloudEvents package

Hardened.CloudEvents is a dependency-free framework package, written by the GCP agent

Eventarc, Pub/Sub through Eventarc, Cloud Storage and Firestore all arrive as CloudEvents; Azure Event Grid delivers CloudEvents JSON to the worker. One small package parses the structured JSON form and the binary HTTP-header form, with a source-generated serializer context so it stays AOT-clean, and maps source, type and subject to a route. No dependency on the CloudNative SDK.

Recommendation: lives at src/Functions/Hardened.CloudEvents, created through the first shared-change request so the Azure agent can consume it for [Event]. If no: each line parses its own envelope and Event Grid and Eventarc drift.

Rules the agents run under

  • Build the way CI does before every gate report. dotnet build Hardened.slnx --configuration Release -p:ContinuousIntegrationBuild=true, then the tests in the agent's own filter, then the public API test. Exit codes, not the tail of the log, per AGENTS.md.
  • Copy the AWS line's conventions, not its types. Package per adapter family, buildTransitive targets binding one property, a module per adapter with equality by type, a serializer context per adapter, IsAotCompatible on every runtime package, a conformance enrolment per request type, tests named for behaviour.
  • Every generator test compiles its output. GeneratorTestHarness.Run(...).AssertNoErrors(), the rule from docs/design/testing-conventions.md.
  • Assert partial batch failures by identifier, never by count.
  • Report contradictions, do not encode them. A cloud behaviour that does not fit a neutral trigger is a NOTICE and a documented divergence, not a null image or a silent default.
  • Never edit a shared member directly, even a one-line one. The worktree isolation enforces it; the rule exists so the agent writes the SCR instead of working around it.
  • Rebase on main at every ACK and every phase gate.

The generator

Per handler carrying a neutral trigger, and once for the web verbs, it emits into the application's assembly:

  1. A shim method with [Function("Queue_orders")] and the real binding attribute built from the trigger's arguments and the module's properties, whose body hands the raw trigger input and FunctionContext to FunctionsInvocationHandler with the route it was generated for. Because every handler has its own function, Azure never needs a payload peek: the function identity is the route.
  2. An IFunctionMetadataProvider returning the same functions with Name, EntryPoint, ScriptFile, Language = dotnet-isolated and RawBindings as JSON, registered by the runtime's UseHardened. This is the metadata the host indexes.
  3. An IFunctionExecutor switching on function id and calling the shims directly, so no reflection stands between the host and the handler and the path survives Native AOT.

Through CSharpAuthor, per the repository rule. Diagnostics: HRDF001 stays the one voice for an unbound trigger; HRDAZ001 is a bound trigger with no Azure binding, HRDAZ002 a function-name collision (case-insensitive, as the host compares), and HRDAZ003, a binding that needs a setting the module did not supply, arrives with the first binding that needs one in Phase 2. The generator's own tests compile every emitted shape, and one test in the Azure integration fixture asserts that the metadata the provider returns equals what the SDK's build task wrote to functions.metadata from the same shims.

Found in Phase 1: the precedence risk did not bite. With worker indexing on, the host indexes the generated provider's list, the SDK's task still writes functions.metadata from the compiled shims, and the two agree; the SDK's own generators still run and emit an empty provider and executor that nothing registers, which is harmless. The shim signature needs no reshaping: raw trigger data plus FunctionContext is what the extension generation scans and what BindInputAsync binds. The Functions host image is amd64-only, so the local container rung runs under Rosetta on Apple Silicon, about twenty seconds to start, while CI runs it natively.

Spike S1, before anything else

A [Queue("orders")] handler, the generator, the Service Bus adapter and the Functions host container over Azurite and the Service Bus emulator. Exit criteria, each a test that stays: the host indexes exactly the functions the provider declares; a message published to the emulator reaches the handler through Hardened's executor; functions.metadata and the provider agree; a thrown handler abandons the batch and the message is redelivered. If the worker's settlement service or the extension generation needs the shim signatures to be something other than raw trigger data, the spike says so and the adapter seam is shaped around it before Phase 2.

6. The GCP line gcp agent

Shape

Everything reaches a Cloud Run service as HTTP, so the request is already a FeatureExecutionRequest from Kestrel. The line is a global filter in front of routing that recognises an envelope, builds a trigger-shaped request from it (Clone cannot replace a body, so a wrapping request type does), and lets the pipeline route QUEUE /orders exactly as it would on Lambda. Failure policy needs no work: Kestrel answers 500 on a throw, Pub/Sub and Eventarc treat anything outside 102, 200, 201, 202 and 204 as a negative acknowledgement, and Scheduler retries per job. A validation refusal is a 400 and therefore also a redelivery, which matches what the SQS fork does today.

Spike S2, before anything else

A [Queue("orders")] handler on [CloudRunRuntime], published, run in mcr.microsoft.com/dotnet/aspnet:8.0 with PORT set, on a Testcontainers network with the Pub/Sub emulator holding a push subscription whose endpoint is the container. Exit criteria: a message published through the Google SDK against the emulator reaches the handler; a thrown handler is redelivered; SIGTERM to the container lets an in-flight request finish. The third criterion is what produces the Kestrel SCR.

Fixtures, AOT, template, docs

  • Integration fixtures under src/Clouds/Gcp/IntegrationTests: Queue, Topic, Timer, Event, Change, Blob, Invoke, Web, each with the AWS twin's test bodies.
  • Hardened.IntegrationTests.Aot.CloudRun.SUT: the existing Kestrel AOT proof already covers the socket; this one serves a Pub/Sub push through the front door, and the CI probe posts one.
  • Template: hardened-function --host gcp and hardened-web --host cloud-run, both with a Dockerfile, PORT handling and a README that shows gcloud run deploy without any IaC. Local run is dotnet run on 8080.
  • Docs: docs/gcp/** with the same page set, and the two divergences written down: no [Stream] on GCP, and Queue versus Topic per D5.

L0 to L2 exist for AWS and are copied per line. L3 is the new rung and the shared harness is the orchestrator's deliverable: Hardened.Functions.Testing.Containers, over Testcontainers, gives a test project a network, the emulator containers it names, the published application mounted into a host image, log capture, readiness, and an observation channel. The channel is the same trick the AOT probe already uses: the fixture's handlers record through an IObservationSink that prints one marked line per invocation to the container's stdout, and the harness tails it, so a test reads await observed.Handled("queue:a-1") where an L0 test read a [Mock].

Container tests live in their own projects and, found in Phase 1, in their own solution: Hardened.Simulators.slnx, one folder per cloud. The plan's trait filter was tried first and filters nothing on the pinned SDK with xunit.v3 3.2.2 and xunit.runner.visualstudio 3.1.5, in either direction, so a project split is the only split CI can rely on. The coverage step runs Hardened.slnx; a Simulators step in the same job restores, builds and tests the second solution afterwards. Both keep the no-skip rule; a test that cannot find Docker fails, as the DynamoDB tests always have. Coverage is not collected for the simulator tier, because the code under test runs in another process.

The lower rungs share one test file: a class-level testing attribute is read off the declaring type, so a derived class cannot raise the fidelity of inherited tests, and the convention both lines settled on is two test projects linking one file, one at L0 with [FunctionTesting] and one at L1 with the provider's attribute, plus [PipelineDelivery] (SCR-204) for a single class that wants the neutral delivery inside an envelope-level assembly.

11. Out of scope

  • Infrastructure as code for either cloud (no CDK equivalent, no Bicep, no Terraform), per the August constraint.
  • Service clients and stores: nothing like the old DynamoDB client package for Cosmos, Firestore or Storage.
  • Durable Functions, Pub/Sub pull as a long-running worker, Event Grid namespaces and MQTT, Azure Container Apps as a tested host (it works through PORT on Kestrel but is not verified here).
  • A LocalStack event-source-mapping tier for AWS.
  • Rewriting docs/aws, which still documents Hardened.Amz. The orchestrator can take it between merges if wanted; it is not part of the two lines.
